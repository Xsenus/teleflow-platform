# Artifact Trust & Signed Evidence

Документ описывает криптографический контур TeleFlow Platform 1.7.0 для подтверждения происхождения и неизменности переносимых артефактов.

## 1. Цель

В версиях до 1.7 ZIP-архивы и JSON-акты содержали SHA-256. Это позволяло обнаружить повреждение после формирования, но не отвечало на вопрос, кто сформировал файл. Версия 1.7 добавляет detached-подобный контейнер `SIGNATURE.json` на Ed25519 и локальную модель доверия.

Контур применяется к:

- configuration bundle;
- диагностическому support bundle;
- JSON-акту приёмки pilot program.

Подпись не превращает содержимое в секретное. Она подтверждает целостность и владение соответствующим приватным ключом. Конфиденциальные данные по-прежнему должны исключаться из артефакта или передаваться по защищённому каналу.

## 2. Криптографическая модель

Используется Ed25519 из библиотеки `cryptography`.

При генерации создаются:

- 32-байтовый приватный ключ;
- 32-байтовый публичный ключ;
- SHA-256 fingerprint публичного ключа;
- стабильный `key_id`, построенный из начала fingerprint.

Приватная часть сохраняется только в зашифрованном виде через существующий AES-256-GCM `SecretCipher`. AAD содержит ID записи:

```text
artifact-signing-key:<database-id>:private
```

API и веб-интерфейс никогда не возвращают `private_key_enc` или расшифрованную приватную часть.

## 3. Контейнер подписи

`SIGNATURE.json` имеет фиксированную схему:

```json
{
  "schema_version": 1,
  "algorithm": "Ed25519",
  "purpose": "teleflow.configuration_bundle.manifest.v1",
  "key_id": "ed25519-...",
  "fingerprint_sha256": "...",
  "public_key_b64": "...",
  "signed_sha256": "...",
  "created_at": "2026-08-06T12:00:00+00:00",
  "signature_b64": "..."
}
```

Подписывается не один digest, а доменно-разделённая каноническая структура всех метаданных:

```text
TeleFlow-Artifact-Signature-v1\n
<canonical JSON metadata>
```

Это означает, что изменение `purpose`, `created_at`, `key_id`, fingerprint, public key или digest обнаруживается при проверке.

## 4. Назначение подписи

Каждый тип артефакта имеет собственный `purpose`:

```text
teleflow.configuration_bundle.manifest.v1
teleflow.support_bundle.manifest.v1
teleflow.pilot_acceptance.payload.v1
```

Подпись одного типа нельзя перенести на другой тип файла: verifier сверяет точное назначение до принятия результата.

## 5. Что именно подписывается

### Configuration bundle

Подписывается канонический JSON `manifest.json`. Manifest содержит SHA-256 всех payload-файлов, поэтому подпись транзитивно защищает весь архив.

Проверка включает:

1. безопасные ZIP-пути;
2. отсутствие symlink, encrypted entries и дубликатов;
3. точное совпадение состава ZIP и manifest;
4. SHA-256 каждого файла;
5. Ed25519-подпись manifest;
6. локальный статус доверия или отзыва ключа.

### Support bundle

Подписывается байтовое содержимое `MANIFEST.sha256`. Затем verifier сверяет каждый перечисленный файл и запрещает незаявленные файлы.

### Pilot acceptance report

Подписывается канонический `payload`. Manifest акта строго ограничен полями:

```text
algorithm
payload_sha256
generated_at
```

Verifier требует `SHA-256`, совпадение `generated_at` с payload и отсутствие неизвестных полей верхнего уровня.

## 6. Локальная модель доверия

Криптографически корректная подпись и доверенная подпись — разные состояния.

```text
unsigned
valid_untrusted
valid_trusted
invalid
revoked
```

Публичный ключ может быть:

- сгенерирован локально вместе с приватной частью;
- импортирован только как публичный ключ;
- отмечен доверенным для импорта;
- назначен основным, если локальная приватная часть существует;
- отозван.

Отзыв:

- снимает статус основного;
- снимает доверие;
- уничтожает зашифрованную приватную часть;
- сохраняет публичный ключ и fingerprint для проверки исторических файлов;
- запрещает новые подписи и доверенный импорт этим ключом.

## 7. Политики

Переменная:

```text
TELEFLOW_ARTIFACT_SIGNATURE_POLICY
```

Допустимые значения:

### `optional`

Разрешает legacy-артефакты без подписи. Недействительная или отозванная подпись всё равно блокируется.

### `require_valid`

Требует криптографически корректную подпись, но не требует локального trust record.

### `require_trusted`

Требует криптографически корректную подпись активным ключом, который явно доверен организации.

Production-конфигурация принудительно использует:

```text
TELEFLOW_ARTIFACT_SIGNATURE_POLICY=require_trusted
```

Приложение отказывается стартовать в production с более слабой политикой.

## 8. Жизненный цикл ключа

### Генерация

Owner или Admin создаёт локальный ключ. По умолчанию он может стать основным и доверенным.

### Экспорт публичной части

Публичная часть доступна как base64 и PEM. Это единственная часть, которую следует передавать другой инсталляции.

### Импорт доверия

Получатель импортирует PEM/base64, сверяет fingerprint по независимому каналу и только затем включает `trusted_for_import`.

### Смена основного ключа

Новый локальный ключ назначается основным. Старый можно оставить активным для проверки переходного периода либо отозвать.

### Отзыв

Отзыв необратим для приватной части. Для продолжения подписания необходимо создать новый ключ.

## 9. Master-key rotation

`private_key_enc` входит в штатную ротацию master key:

```bash
TELEFLOW_NEW_MASTER_KEY='<new-key>' \
python scripts/rotate_master_key.py --dry-run

TELEFLOW_NEW_MASTER_KEY='<new-key>' \
python scripts/rotate_master_key.py --yes
```

Dry-run проверяет возможность расшифровать текущую приватную часть. В консоль не выводится plaintext ключа.

## 10. Автономная проверка

Проверить файл без запуска API:

```bash
python scripts/verify_artifact.py artifact.zip --json
```

Потребовать любую действительную подпись:

```bash
python scripts/verify_artifact.py artifact.zip --json
```

Разрешить legacy-файл без подписи:

```bash
python scripts/verify_artifact.py artifact.zip --allow-unsigned --json
```

Потребовать доверенный fingerprint:

```bash
python scripts/verify_artifact.py artifact.zip \
  --trusted-fingerprint '<sha256-fingerprint>' \
  --require-trusted \
  --json
```

Использовать PEM:

```bash
python scripts/verify_artifact.py artifact.zip \
  --trusted-public-key trusted-ed25519.pem \
  --require-trusted \
  --json
```

Коды завершения:

```text
0 — артефакт принят выбранной политикой
1 — целостность сохранена, но политика доверия не выполнена
2 — файл повреждён, неизвестен или не может быть проверен
```

## 11. Проверка через API

```text
GET  /api/v1/artifact-signing-keys
POST /api/v1/artifact-signing-keys/generate
POST /api/v1/artifact-signing-keys/import
PATCH /api/v1/artifact-signing-keys/{id}
POST /api/v1/artifact-signing-keys/{id}/default
POST /api/v1/artifact-signing-keys/{id}/revoke
GET  /api/v1/artifact-signing-keys/{id}/public
POST /api/v1/artifact-signing-keys/verify-artifact
```

Проверка через API учитывает локальный trust store и показывает, известен ли signer и отозван ли соответствующий ключ.

## 12. Commissioning

Commissioning 1.7 проверяет:

- наличие активного ключа;
- наличие основного ключа с локальной приватной частью;
- явное доверие основному ключу при `require_trusted`;
- выбранную policy.

Отсутствие подходящего ключа становится blocker для production commissioning.

## 13. Операционная процедура передачи

1. Источник генерирует локальный ключ.
2. Источник экспортирует публичный PEM.
3. Получатель сверяет fingerprint по независимому каналу.
4. Получатель импортирует публичный ключ как trusted.
5. Источник создаёт подписанный архив.
6. Получатель проверяет файл автономно до импорта.
7. Получатель выполняет preview через TeleFlow.
8. Только после двух успешных проверок выполняется fail-safe import.

## 14. Incident response

При подозрении на компрометацию:

1. включить emergency publishing stop при наличии риска для рабочей инсталляции;
2. отозвать ключ;
3. сохранить fingerprint и список ранее подписанных артефактов;
4. создать новый ключ;
5. передать новый публичный ключ по независимому каналу;
6. удалить доверие к старому ключу на принимающих инсталляциях;
7. повторно сформировать критичные configuration bundles и акты;
8. проверить audit-chain.

## 15. Ограничения

- Ed25519 не шифрует содержимое.
- Встроенный public key доказывает криптографическую целостность, но доверие возникает только после независимой сверки fingerprint.
- Отзыв является локальным. Централизованного PKI/CRL в self-hosted core нет.
- Скомпрометированный master key и база могут раскрыть активную приватную часть; поэтому backup, host hardening и master-key rotation остаются обязательными.
- Время подписи подписано, но не является внешней доверенной timestamp-службой.
- Для юридически значимого документооборота может потребоваться отдельная квалифицированная электронная подпись в соответствии с применимым законодательством.
