# Pilot Certification — TeleFlow Platform 1.5

## Назначение

Контур Pilot Certification ограничивает реальный масштаб Telegram-публикаций технически, а не только инструкцией оператору. Он предназначен для последовательного допуска:

```text
LOCAL → SERVICE → FIVE → TWENTY → FIFTY → HUNDRED
```

Пределы означают максимальное количество включённых назначений в одном запуске: `0`, `1`, `5`, `20`, `50`, `100`. Локальный этап разрешает широкий маршрут только при `TELEFLOW_TELEGRAM_FAKE_MODE=true`, когда сетевых запросов к Telegram нет.

Контур не обещает отсутствие ограничений Telegram и не подбирает «антибан-интервал». Он требует разрешение каждой группы, свежую Telegram-проверку, служебную canary-публикацию и фактическое подтверждение предыдущего масштаба.

## Где применяется gate

При `TELEFLOW_PILOT_STAGE_ENFORCEMENT_REQUIRED=true` лимит проверяется:

1. в preview кампании;
2. при утверждении и ручном запуске;
3. при возобновлении кампании;
4. scheduler перед созданием run;
5. при раскрытии следующего staged-пакета;
6. Safety Engine непосредственно перед созданием Telegram gateway.

Таким образом, старый UI, прямой API-вызов и уже ожидающее задание не обходят актуальный этап.

## Служебная canary-проверка

Canary — единичное фиксированное сообщение в собственной или явно разрешённой служебной группе.

Оператор не вводит произвольный текст. Система формирует сообщение с уникальным маркером:

```text
TeleFlow — служебная проверка публикации
Маркер: TF-CANARY-...
Это единичное тестовое сообщение в заранее разрешённой группе.
Автоматический повтор отключён. Сообщение можно удалить после проверки.
```

Перед единственным сетевым запросом проверяются:

- роль Owner/Admin и CSRF;
- активность организации и отсутствие emergency stop;
- активность подключения и назначения;
- подтверждённое основание разрешения;
- срок разрешения;
- свежая Telegram-валидация и наличие chat ID;
- blackout-календарь;
- локальное временное окно назначения;
- canary cooldown;
- FloodWait, minimum interval и cooldown группы;
- дневной лимит подключения и общий hard cap.

Destination и connection блокируются транзакционно на время проверки, чтобы два параллельных запроса не прошли один и тот же cooldown. Автоматического retry нет. `TelegramDeliveryUncertain`, anti-spam, auth error и FloodWait требуют ручной проверки или паузы подключения.

Fake canary сохраняется для проверки интерфейса, но никогда не считается live-доказательством.

## Оценка следующего этапа

Оценку можно создать только для следующего последовательного этапа. Она сохраняет:

- текущий и запрашиваемый этап;
- все checks;
- blockers и warnings;
- summary;
- SHA-256 fingerprint текущего состояния;
- автора, время создания и TTL.

Проверки включают:

- активность организации;
- отсутствие аварийной остановки;
- выключенный fake mode;
- свежий worker heartbeat;
- активное и недавно проверенное Telegram-подключение;
- достаточное количество разрешённых и свежепроверенных назначений, каждое со своим здоровым Telegram-подключением;
- свежую успешную реальную canary;
- отсутствие заданий `waiting_review`;
- отсутствие неподтверждённых critical notifications;
- реальный завершённый запуск предыдущего масштаба.

Fake `telegram_message_id` с префиксом `fake-` не учитывается. Для переходов требуется минимум реальных отправок:

| Новый этап | Реальные отправки предыдущего пилота |
|---|---:|
| SERVICE | 0, достаточно live canary |
| FIVE | 1 |
| TWENTY | 5 |
| FIFTY | 20 |
| HUNDRED | 50 |

Доля ошибок должна быть не выше `TELEFLOW_PILOT_MAX_FAILURE_PERCENT`, а доказательство запуска — не старше `TELEFLOW_PILOT_RUN_EVIDENCE_MAX_AGE_DAYS`.

## Fingerprint и подтверждение

Перед повышением сервер повторно вычисляет fingerprint. Любое изменение подключений, готовых назначений, срока разрешения, Telegram validation, canary, результата пилота, количества неоднозначных доставок, свежести worker heartbeat, неподтверждённых critical events или статуса организации делает оценку устаревшей.

Повышение требует точную фразу:

```text
ПЕРЕЙТИ НА ЭТАП N
```

Понижение требует:

```text
СНИЗИТЬ ЭТАП ДО N
```

При понижении кампании выше нового лимита ставятся на паузу, а ожидающие/удержанные задания переводятся в `waiting_review` без Telegram-запроса.

## Диагностический support bundle

Owner/Admin может создать временный ZIP для технической поддержки. Архив включает только обезличенные operational metadata:

- runtime и безопасные флаги конфигурации;
- статус организации и pilot stage;
- подключения без имени и credentials;
- назначения без title/username/chat ID/rules URL;
- кампании без имени и текста;
- агрегаты queue/run;
- последние readiness/stage/canary статусы;
- агрегаты уведомлений;
- результат проверки audit hash-chain;
- внутренний `MANIFEST.sha256`.

UUID заменяются стабильными псевдонимами внутри организации. Архив не содержит:

- Bot token, `api_hash`, StringSession, коды и пароли Telegram;
- JWT/master keys/TOTP/API keys;
- тексты шаблонов, публикаций или диалогов;
- телефоны, email, имена кандидатов и пользователей;
- raw audit details;
- credentials интеграций, S3 или AI.

Файл отдаётся с `Cache-Control: no-store`, проверяется по SHA-256, автоматически истекает и удаляется retention worker. Его можно удалить вручную раньше срока.

## Роли

| Операция | Viewer | Operator | Admin | Owner |
|---|---:|---:|---:|---:|
| Просмотр этапа/оценок/canary | ✓ | ✓ | ✓ | ✓ |
| Создание оценки | — | — | ✓ | ✓ |
| Повышение/понижение этапа | — | — | ✓ | ✓ |
| Служебная canary | — | — | ✓ | ✓ |
| Создание/скачивание support bundle | — | — | ✓ | ✓ |

Все write-операции дополнительно защищены CSRF, tenant isolation и audit logging.

## Production-настройки

```env
TELEFLOW_PILOT_STAGE_ENFORCEMENT_REQUIRED=true
TELEFLOW_PILOT_STAGE_ASSESSMENT_TTL_MINUTES=30
TELEFLOW_PILOT_CANARY_COOLDOWN_HOURS=24
TELEFLOW_PILOT_CANARY_VALID_HOURS=168
TELEFLOW_PILOT_RUN_EVIDENCE_MAX_AGE_DAYS=30
TELEFLOW_PILOT_MAX_FAILURE_PERCENT=10
TELEFLOW_SUPPORT_BUNDLE_TTL_HOURS=24
```

Production runtime отказывается запускаться, если stage enforcement выключен.

## Обновление существующей установки

Migration 1.5 сохраняет существующим организациям прежний эффективный лимит `HUNDRED`, чтобы обновление не изменило активный маршрут молча. Новые организации начинают с `LOCAL`.

Для фактической сертификации существующей организации Owner должен вручную понизить этап до `LOCAL` или `SERVICE`, зафиксировать причину и пройти последовательность заново. Перед этим необходимо включить emergency stop и разрешить все неоднозначные доставки.

Это решение совместимости не считается подтверждением безопасности существующих публикаций: оно только не создаёт неожиданную блокировку после миграции.
