# Production Pilot TeleFlow Platform 1.5

## 1. Назначение

Контур Production Pilot не заменяет разрешение администраторов Telegram-групп и не обещает отсутствие ограничений Telegram. Его задача — не допустить запуск кампании, пока локальная конфигурация, права, расписание и операционная инфраструктура не прошли проверяемый набор условий.

Платформа предназначена только для групп, каналов и тем, где публикации разрешены правилами или администраторами. Auto-join, ротация аккаунтов и прокси, массовые личные сообщения и обход ограничений Telegram не реализованы.

## 2. Жизненный цикл допуска

Рекомендуемый порядок для каждой кампании:

```text
подключение Telegram
→ добавление разрешённых назначений
→ фиксация основания и срока разрешения
→ повторная проверка доступа Telegram
→ подготовка шаблона и маршрута
→ preflight
→ утверждение кампании
→ Production Pilot readiness
→ staged rollout
→ checkpoint
→ расширение маршрута
```

Отчёт готовности имеет ограниченный TTL и связан с криптографическим fingerprint кампании. Изменение текста, маршрута, расписания, подключения, A/B-варианта или правил назначения делает старый отчёт непригодным для запуска.

## 3. Проверки readiness

Сохраняемый отчёт проверяет:

1. активность организации и состояние глобального аварийного стопа;
2. свежесть heartbeat worker;
3. статус Telegram-подключения и наличие зашифрованных credentials;
4. свежесть health-check подключения в live mode;
5. актуальность утверждения и campaign fingerprint;
6. новый persisted preflight;
7. число независимых Owner/Admin для выбранной approval policy;
8. staged rollout для маршрутов выше заданного порога;
9. свежесть повторной проверки каждого назначения;
10. действующие операционные запреты;
11. соответствие маршрута дневным caps;
12. TOTP владельцев и администраторов.

Результаты:

- `passed` — blockers и warnings отсутствуют;
- `warning` — запуск допустим политикой, но оператор должен оценить предупреждения;
- `blocked` — запуск запрещён.

В fake mode readiness подтверждает только локальную готовность. Он не доказывает реальные права Telegram.

## 4. Повторная проверка назначений

После успешного `resolve_destination` сохраняются:

- время проверки;
- срок действия результата;
- Telegram chat ID, username, тип назначения;
- доступные capabilities;
- пользователь и источник проверки;
- код и текст ошибки при неуспехе.

Проверка может выполняться отдельно или пакетом до 50 назначений. Если Telegram возвращает обязательное ожидание, оставшаяся часть пакета получает статус `deferred` и не отправляет дополнительные запросы.

`CHAT_WRITE_FORBIDDEN` классифицируется отдельно как `write_forbidden`, отключает назначение и требует ручной проверки. Обычная временная или конфигурационная ошибка получает `failed`.

Срок результата задаётся:

```env
TELEFLOW_DESTINATION_VALIDATION_TTL_HOURS=168
```

В production устаревшая проверка блокирует preflight, readiness, scheduler и Safety Engine перед Telegram network call.

## 5. Операционный календарь

Окна запрета поддерживают три уровня:

- вся организация;
- конкретное Telegram-подключение;
- конкретное назначение.

Виды окна:

- разовое UTC-окно `starts_at` → `ends_at`;
- еженедельное локальное окно с IANA timezone, днями недели и временем.

Еженедельное окно может пересекать полночь. Например, четверг `22:00–07:00` действует с четверга 22:00 до пятницы 07:00.

Если запрет активен, Safety Engine не создаёт Telegram gateway и не увеличивает счётчик реальных попыток. Задание переносится на окончание самого позднего совпавшего окна.

## 6. Обязательный readiness gate

Для production-конфигурации:

```env
TELEFLOW_PILOT_READINESS_REQUIRED=true
TELEFLOW_READINESS_TTL_MINUTES=30
TELEFLOW_CONNECTION_HEALTH_TTL_HOURS=24
TELEFLOW_PILOT_STAGED_THRESHOLD=5
```

При включённом gate:

- `run-now` и `resume` возвращают конфликт без актуального отчёта;
- scheduler ставит due-кампанию на паузу, если отчёт отсутствует, истёк или имеет другой fingerprint;
- создаются критические audit/notification events;
- после исправления причин оператор создаёт новый readiness report и заново запускает кампанию.

## 7. Web UI

Раздел **Production Pilot** показывает:

- активные подключения;
- состояние worker;
- назначения с просроченной проверкой;
- истёкшие и скоро истекающие разрешения;
- активные окна запрета;
- последние readiness reports;
- blockers и warnings по каждой кампании;
- историю проверки выбранного назначения;
- пакетную повторную проверку;
- создание, редактирование, отключение и удаление blackout-окон.

Изменяющие операции доступны только соответствующим ролям и защищены CSRF/RBAC/tenant isolation.

## 8. Пилотный ввод

Рекомендуемая последовательность:

```text
fake mode
→ служебный Bot API чат
→ отдельный рабочий MTProto-аккаунт
→ 5 разрешённых назначений
→ ручной checkpoint
→ 20
→ 50
→ 100
```

До расширения необходимо проверить журнал, отсутствие жалоб, правила групп, фактическую доставку, обработку SlowMode/FloodWait и возможность немедленной остановки.

## 9. Ограничения доказательности

Локальный readiness не подтверждает:

- что администратор группы не изменил правила после проверки;
- что Telegram не применит новое ограничение после запуска;
- что публикация желательна аудитории;
- что внешний webhook, AI, Google Sheets или S3 доступны без live credentials;
- что production backup действительно восстанавливается без restore drill.

Поэтому readiness является дополнительным операционным барьером, а не заменой ручного контроля и live-пилота.

## Продолжение в версии 1.5

Readiness 1.4 отвечает на вопрос «готова ли конкретная кампания сейчас». Pilot Certification 1.5 добавляет отдельный вопрос «какой live-масштаб организация уже доказала». Оба gate обязательны:

```text
pilot stage допускает размер маршрута
        +
readiness/preflight допускают конкретную кампанию
        =
возможность постановки в очередь
```

Подробный workflow, canary и support bundle описаны в [PILOT_CERTIFICATION.md](PILOT_CERTIFICATION.md).
