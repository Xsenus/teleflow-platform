# Controlled Operations — preflight, staged rollout и reconciliation

Документ описывает операционный контур TeleFlow Platform 1.3. Он применяется и к Bot API, и к пользовательскому MTProto-подключению.

## 1. Срок действия разрешения назначения

Для каждой группы можно сохранить:

- статус разрешения;
- текстовое основание;
- ссылку на правила;
- время последней проверки;
- необязательное время окончания разрешения.

После истечения срока:

1. preflight помечает назначение блокирующим;
2. scheduler не создаёт run;
3. Safety Engine блокирует уже существующий job до Telegram network call;
4. оператор должен повторно проверить правила/согласование и заново подтвердить разрешение;
5. изменение входит в campaign fingerprint и требует нового утверждения.

Перевод назначения в `unverified` или `denied` очищает срок и данные подтверждения.

## 2. Persisted preflight

Preflight сохраняет:

- fingerprint кампании;
- итоговый статус `passed`, `warning`, `blocked` или `expired`;
- общие blockers/warnings;
- отдельный результат по каждой группе;
- расчётное время;
- номер пакета;
- content fingerprint;
- срок разрешения;
- ссылку на найденный недавний duplicate job;
- время создания и окончания действия отчёта.

Проверяются только детерминированные локальные условия. Реальные Telegram-права и ограничения всё равно повторно проверяются gateway/Safety Engine при доставке.

### Почему scheduler всегда создаёт новый отчёт

Approval fingerprint защищает конфигурацию от изменения, но не фиксирует ход времени. Даже при неизменной кампании могли:

- истечь разрешение группы;
- появиться идентичная отправка;
- измениться cooldown/allowed window;
- исчезнуть media object;
- быть отозваны локальные права назначения.

Поэтому отчёт, созданный при утверждении, не используется как единственное основание для будущего запуска.

## 3. Content fingerprint и duplicate guard

Fingerprint строится из нормализованного снимка:

```text
body
parse mode
media SHA-256
link preview flag
```

Нормализация не «размножает» текст и не применяется для обхода модерации. Она только устраняет незначимые различия пробелов и регистра при локальной проверке дублей.

Проверка выполняется:

1. в preview/preflight;
2. повторно непосредственно перед отправкой job.

Поиск ограничен одной организацией и одним назначением. При найденном дубле job получает `skipped / DUPLICATE_CONTENT`; Telegram network call не выполняется.

## 4. Staged rollout

Кампания может работать в режимах:

- `standard` — все jobs создаются доступными последовательной очереди;
- `staged` — доступен только активный пакет, остальные имеют статус `held`.

Параметры staged режима:

- размер пакета;
- пауза перед раскрытием следующего пакета;
- ручной checkpoint после каждого пакета;
- допустимый процент неуспешных результатов.

`held` jobs не выбираются worker и не превращаются в pending без функции `release_next_batch` или административного checkpoint endpoint.

### Ручной checkpoint

Перед продолжением оператор проверяет:

- сообщения появились в ожидаемых темах;
- администраторы не удалили публикации;
- нет неожиданных дублей;
- нет critical/waiting-review jobs;
- нет признаков жалоб или ограничений;
- содержимое соответствует утверждённому снимку.

Checkpoint фиксирует пользователя, время и комментарий в run/audit.

### Автоматический переход

Разрешён только если ручной checkpoint отключён и доля неуспешных результатов не превысила порог. Любой `waiting_review` остаётся nonterminal и блокирует переход.

### Controlled abort

Owner/Admin может остановить активный staged run. Операция:

- запрещена, пока job находится в `processing`;
- отменяет `held`, `pending`, `retry` и допустимые `waiting_review` jobs;
- переводит run в `cancelled`;
- ставит кампанию на паузу;
- снимает прежнее утверждение;
- создаёт audit/notification.

## 5. Ручная сверка неоднозначной доставки

Сетевой разрыв после Telegram request не позволяет надёжно определить, принято ли сообщение. Автоматический retry в таком состоянии опасен дублем.

Job получает:

```text
status = waiting_review
error_code = DELIVERY_RESULT_UNCERTAIN
```

Доступны три решения:

### `confirmed_sent`

Оператор нашёл сообщение в группе и указывает Telegram message ID. Job становится `sent`, обновляются cooldown/last delivery.

### `confirmed_not_sent`

Оператор проверил целевой чат и уверен, что сообщения нет. Только после проверки connection/approval/permission job получает один явно разрешённый `retry`.

### `skipped`

Результат сознательно закрывается без повторной отправки.

Каждое решение сохраняет reviewer, timestamp, note и не может быть заменено обычной кнопкой retry. Пока сверка не завершена:

- campaign cancel и staged abort возвращают `409`;
- редактирование маршрута/настроек не может скрыть результат;
- отзыв Telegram-подключения уничтожает credentials, но сохраняет uncertain job;
- после отзыва доступны `confirmed_sent` или `skipped`, а `confirmed_not_sent` не создаёт retry без активного подключения;
- reconciliation обновляет счётчики, но не возрождает уже отменённый run.

## 6. Рекомендуемый пилот

```text
1 служебная группа
→ 5 разрешённых групп, batch size 5, manual checkpoint
→ 20 групп, небольшие пакеты
→ 50 групп
→ 100 групп только после отдельных acceptance gates
```

Рекомендуемые значения по умолчанию панели:

```text
rollout_mode=staged
rollout_batch_size=5
rollout_require_checkpoint=true
rollout_failure_threshold_percent=20
rollout_pause_seconds=300
duplicate_guard_minutes=1380
```

Это не гарантирует отсутствие ограничений Telegram. Главные условия — релевантность, согласование с администраторами, соблюдение правил каждой группы и остановка при любом safety event.
